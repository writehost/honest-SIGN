# SCADA Mini WMS — architecture map

Облачная WMS для селлеров WB / Ozon / Яндекс Маркета со складом на 1–10 человек.
Главная ценность: **складской учёт и защита от пересорта без покупки ТСД** — телефон и есть терминал.

## 1. Продуктовые решения

| Решение | Почему |
|---|---|
| Склад → Зона → Ячейка (`A-01-03`) | Хватает маленькому складу. Нет уровней, ярусов, типов ячеек. |
| Остаток = `StockBalance(product, location, qty, reserved)` | Источник истины «что, где, сколько». Никакого `Product.quantity`. |
| Любое изменение остатка пишет `StockMovement` | Журнал «кто/когда/что/откуда/куда» и остатки не могут разойтись. |
| 6 статусов заказа | Новый → К сборке → Собирается → Собран → Упакован → Отгружен. |
| Два барьера от пересорта | Сборка: скан ячейки → скан товара. Упаковка: повторный скан каждой единицы. Ошибку нельзя «прожать». |
| Резерв при передаче в сборку | Резерв привязан к ячейке; маршрут сборки строится сразу. Перемещение зарезервированного товара запрещено. |
| Короб заказа (`BOX-0001`) или QR заказа | Отобранное лежит в локации-коробе, привязанном к заказу. Параллельная сборка не смешивается. |
| 2 роли: Владелец, Кладовщик | Без RBAC. Расширенные права — тариф Pro, Later. |
| Предупреждение vs блок | Не та ячейка при приёмке — предупреждение с явным выбором. Неверный товар при сборке/упаковке — блок без обхода. |

## 2. Карта системы

```
 Телефон (PWA, Android/iOS)        Компьютер владельца (браузер)
 ┌──────────────────────────┐      ┌──────────────────────────────┐
 │ Терминал /m              │      │ Кабинет /app                 │
 │ приёмка · сборка ·       │      │ товары · остатки · заказы ·  │
 │ упаковка · перемещение · │      │ ячейки+QR PDF · журнал ·     │
 │ инвентаризация · поиск   │      │ импорт CSV · пользователи    │
 │ камера / BT HID сканер   │      │ USB-сканер в поиске          │
 │ outbox (офлайн-очередь)  │      │                              │
 └────────────┬─────────────┘      └───────────────┬──────────────┘
              │ HTTPS JSON, op id = idempotency key │
 ┌────────────▼────────────────────────────────────▼──────────────┐
 │ Modular monolith (FastAPI или Django), один процесс            │
 │  auth · tenancy · catalog · warehouse · stock · orders ·       │
 │  picking · packing · inventory · import · billing(plan limits) │
 │  integrations: MarketplaceConnector (WB/Ozon/ЯМ — Later)       │
 │  фоновые задачи: таблица jobs в Postgres (SKIP LOCKED)         │
 └────────────┬────────────────────────────────────────────────────┘
              │
        PostgreSQL (одна БД, org_id во всех таблицах, RLS)
```

Без Kafka, Kubernetes, Elasticsearch, Redis Streams, микросервисов. Поиск — индексы
`pg_trgm` по названию/SKU и точные индексы по штрихкоду. Redis — только если появится
реальная нужда в кеше. Один VPS (2 vCPU / 4 GB) обслуживает сотни небольших складов.

## 3. Модули (одинаково во фронтенде-прототипе и бэкенде)

| Модуль | Прототип | Отвечает за |
|---|---|---|
| tenancy / org | `services.registerOrganization`, `addUser`, `plans.ts` | Организация, пользователи, тариф и лимиты |
| catalog | `createProduct`, `importProducts`, `deleteProduct` | Товары, штрихкоды (N на товар), архив вместо удаления |
| warehouse | `createCellRange`, `createContainers` | Зоны, диапазоны ячеек, короба |
| stock | `balance`, `record`, `productStock`, `cellContents` | Единственное место, где меняются остатки |
| receiving | `receive`, `suggestCell`, `createReceipt` | Приёмка с документом и без |
| moving | `move` | Перемещение, защита резерва |
| orders | `createOrder`, `releaseOrder`, `shipOrders` | Заказы, резерв, маршрут |
| picking | `startPicking`, `bindContainer`, `confirmPick` | Сборка с проверкой ячейки и товара на сервере |
| packing | `completePacking` | Сверка комплектности, отказ при несоответствии |
| inventory | `diffCell`, `commitCellCount` | Пересчёт ячейки, чужой товар, корректировки |
| lookup | `resolveCode` | Один резолвер скана: ячейка → короб → штрихкод → заказ → SKU → артикул |
| integrations | `connectors.ts` | Интерфейс `MarketplaceConnector`, без реализаций в MVP |

Все сервисы принимают `Ctx { orgId, userId }` и читают данные только через `scope(db, ctx)`.
В бэкенде то же самое обеспечивает Postgres RLS (`app.org_id`), см. `backend/schema.sql`.

## 4. Транзакционность

Каждая операция — одна транзакция: проверки → изменение `stock_balance` → запись
`stock_movement` → смена статусов. В прототипе это `transact()` (работа на копии и атомарная
подмена), в бэкенде — `BEGIN … COMMIT` с `SELECT … FOR UPDATE` по строкам остатка.
Отклонённая операция не оставляет следов (покрыто тестом `refused op leaves no trace`).

Проверки сборки делаются **на сервере**, а не только в UI: `confirmPick` повторно сверяет
ячейку и товар, `completePacking` — количество и лишнее. Обойти интерфейс нельзя.

## 5. Офлайн

* Service worker кеширует оболочку приложения — терминал открывается без сети.
* Текущий шаг операции хранится на устройстве (`usePersistentState`) — блокировка экрана,
  перезагрузка или обрыв связи не теряют приёмку на середине.
* Операции без связи складываются в outbox (`lib/net.ts`) с client id; после восстановления
  отправляются по порядку. Сервер идемпотентен по id и перепроверяет правила; отклонённую
  операцию показывает пользователю. Никакого CRDT/merge-движка.
* Баннер: «Нет связи. Операции временно сохраняются на устройстве».

## 6. Сканирование

* Камера: нативный `BarcodeDetector` (Chrome/Android — быстрый, через ML Kit), иначе ZXing
  (iOS Safari). EAN-13, EAN-8, Code128, QR, DataMatrix, UPC-A.
* Bluetooth/USB сканер в режиме HID: слушаем `keydown` на `window`, буфер сбрасывается при
  паузе > 60 мс, Enter завершает код. Ничего не нужно фокусировать — клавиатура телефона не
  всплывает.
* Ответ: зелёная вспышка + короткий писк + 35 мс вибрации; ошибка — красный полноэкранный
  экран с «Ожидалось / Отсканировано», низкий звук, длинная вибрация, единственная кнопка.

## 7. Мультитенантность и тарифы

`organization.plan` (`start | seller | pro`) + лимиты в `plans.ts`: склады, пользователи,
товары, глубина журнала, флаги интеграций и API. Лимиты проверяют сервисы (`PLAN_LIMIT`).
Биллинг (оплата, счета) — Later.

## 8. API (для бэкенда)

```
POST /api/v1/auth/register            {orgName, userName, email, password}
POST /api/v1/ops                      {id, type, payload}   ← все складские операции, идемпотентно
     type: receive | move | pick.start | pick.bind | pick.confirm | pack.complete | inventory.commit
GET  /api/v1/lookup?code=…            → cell | product | container | order
GET  /api/v1/products?q=  POST/PATCH /api/v1/products  POST /api/v1/products/import
GET  /api/v1/stock?product=|cell=
GET  /api/v1/orders?status=  POST /api/v1/orders  POST /api/v1/orders/{id}/release|ship
POST /api/v1/cells/range  GET /api/v1/cells/labels.pdf?codes=&format=
GET  /api/v1/movements?from=&type=&user=
```

## 9. Android

MVP — PWA (`manifest.webmanifest`, ярлыки «Сборка/Приёмка/Упаковка», standalone, portrait).
Для Google Play / RuStore оборачивается в Trusted Web Activity (Bubblewrap) без отдельного
кода. Нативное приложение имеет смысл только для промышленных ТСД с аппаратным сканером
(Intent API) — Later.

## 10. MVP и Later

**MVP (реализовано в прототипе):** регистрация организации и онбординг за 5 шагов; товары,
штрихкоды, фото, архив, CSV-импорт; ячейки диапазоном и PDF с QR (58×40, 58×30, A4);
сборочные короба; остатки по ячейкам; приёмка (по поставке и без, быстрый режим);
перемещение; сборка с двухшаговой проверкой; упаковка со сверкой; инвентаризация с поиском
пересорта; глобальный поиск/скан; журнал; пользователи и роли; тарифные лимиты; офлайн-очередь.

**Later:** коннекторы Wildberries / Ozon / Яндекс Маркет (интерфейс готов); печать этикеток
маркетплейсов; весы; фотоконтроль; волновая сборка; маршрутизация; аналитика; прогноз
остатков; биллинг; расширенные права; несколько складов в UI; партии/сроки годности;
«Честный знак».
